## Private local workspace

Device backups, firmware releases, private reproduction files, helper scripts and development worktrees live in **`.local-device/`** inside this repository. The directory is excluded by `.git/info/exclude`, independently of the checked-out branch. Before writing private material, verify `git check-ignore .local-device/reader-backup` succeeds. If the local exclude is missing on a new checkout, add `/.local-device/` to `.git/info/exclude` first. Never stage or force-add this directory.

When working in a linked worktree, keep using the shared workspace in the primary checkout, currently `/Users/elijah/src/witch-hunt/.local-device`, rather than creating a nested backup directory in the worktree. Resolve the primary checkout from the parent of `git rev-parse --path-format=absolute --git-common-dir`. References to `.local-device/` in this guide mean that shared workspace. Run source builds from the active worktree and use explicit shared paths for tools, logs, backups and releases. Verify the ignore rule from the primary checkout; use `git rev-parse --git-path info/exclude` instead of treating a worktree's `.git` file as a directory.

Resolve that old prefix to `<repository>/.local-device` before using an old script; do not execute historical flash scripts blindly. `.local-device/relocation-manifest.json` records SHA-256 hashes for the moved files. ## Reflashing this reader

For routine app-only updates use the fast workflow in `docs/flashing-x4pro.md` and `scripts/reader_state_backup.py`: preserve complete reading state, skip untouched library/font/dictionary hashes and known derived caches, and include old web assets only when replacing the bundle. The user explicitly accepts dictionary loss and requests that dictionary checks not delay flashing. Use `--no-stub` for reliable ROM access on this device and explicit `--compress` for the next authorized ESP32-S3 write; retain all identity/slot/rollback/protected-flash/application verification. Return the reader promptly after critical checks. Do not run the old full-library helper by default.

1. Flash only when requested. Do not mistake USB dictionary installation for permission to flash experimental firmware. Preserve the known-good image and verify its hash before using it as rollback.
2. Identify the physical reader, rather than assuming a serial-port name. Expected hardware: **Xteink X4 Pro, ESP32-S3**, MAC `98:c3:77:b9:90:18`, USB serial VID `303a`, PID `1001`. USB serial numbers may contain colons; normalize before comparison. Last observed port: `/dev/cu.usbmodem1401`; rediscover it each time. The original C3 X4 is a different device.
3. If in USB drive mode, back up current settings/progress from the mounted SD card. Identify the card by its volume UUID `085494E0-3B78-3E20-A63C-B3C70B8BC6F5`, not by a reusable disk number. Safely eject before opening the flash tool. This firmware automatically leaves USB drive mode after host eject.
4. Read and save the live partition table (`0x8000`, length `0x1000`) and OTA metadata (`0xe000`, length `0x2000`). Resolve the active application slot from them before writing. Last verified layout: app0 offset `0x10000`, app1 offset `0x650000`, each length `0x640000`. Never assume the old active slot is still active.
5. Confirm chip/device identity, installed image and partition layout. Back up the active app if it does not match a known image. Ensure the new binary fits the actual application partition; the current booksync2 image has 14240 bytes of headroom in that partition.
6. Prefer an **application-only** write to the resolved active slot, preserving bootloader, partition table, NVS, OTA metadata and SD contents. Do not erase all flash or flash a merged image as a routine update. Use esptool's `--flash-mode keep --flash-freq keep --flash-size keep`. Inspect tool help if the CLI version differs.
7. Verify the written application with an independent `verify-flash`, read back and compare the partition table, reset, capture boot logs to check for crashes, and independently confirm the running version through Settings or the web API. Record the exact image hash and results in a new local release manifest. Do not claim physical button, touch, or rendering validation unless actually observed or confirmed by the user.

- Preserve live partition-table, OTA-metadata and any required application readbacks in `reader-backup/`, named for the operation. Keep previous rollback releases intact. Do not overwrite the only copy of a known-good image.
- Create a new `<version>-release/` directory containing the exact application binary, `SHA256SUMS`, a `release-manifest.json`, source provenance, and validation evidence. Capture the Git base commit, branch, SDK revision, dirty status, a patch of tracked changes and copies/hashes of relevant untracked source files; a commit hash alone is insufficient when the build includes uncommitted changes. Exclude all EPUBs, books, secrets and `.local-device/` itself from source snapshots.
- Record version, build environment, byte size, SHA-256, device identity, application offset/partition size, features, tests, independent review where requested, limitations and backup paths. Initially mark `installed` and `firmware_flashed` false. Set each to true only after the corresponding action and verification succeeds; record boot, partition and user/device checks separately. A successful compile is not a successful flash, and successful boot is not visual verification.
- For upstream 2.40-based builds, also preserve the matching `.pio/build/<environment>/web-<hash>.bin` beside the firmware and record its size/hash in the release manifest. These development builds have no published bundle to download automatically. On a future authorized install, back up the existing `/.crosspoint/web/` directory, copy the exact bundle to the SD root and install through `/setup` (or the documented card-source API), then verify the installed bundle status. Firmware compilation alone does not install these assets. See `docs/webserver-endpoints.md` for the current protocol.
- Keep build/test logs and review results under the release's `validation-logs/`. Keep full private serial captures separately in `reader-backup/`; only sanitized excerpts belong in a shareable release. If producing an archive, exclude private data and verify its contents and checksums.
- For SD-card changes such as fonts, dictionaries or settings: snapshot affected existing files first, record exactly what changed, verify copied file hashes, and safely eject. Preserve other dictionaries/fonts and reading progress. If the device is disconnected, stage the files plus an explicit pending-install record; never claim they are already installed.
- Update `.local-device/README-local.md` and the local work-status/installation record with the latest verified installed version, known rollback image, current source branch, outstanding work and pending device checks. Update the known-installed section of this guide when appropriate, without exposing private content.
- Historical manifests and checksum-protected archives are evidence: do not silently rewrite them. Add a new operation record for corrections or path migrations. Do not rerun old installation scripts without adapting their paths and checking their preconditions against the current device.

All of these records stay Git-ignored. Do not commit or push any private EPUB, backup, device dump, binary release or local archive. The sole EPUB exception is the synthetic fixture named above. Do not commit or push source changes without the user's permission.
